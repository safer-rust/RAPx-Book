# Chapter 8.6. Limitations

A `SOUND` result means that every obligation RAPx checked was proved. This chapter describes what such a result does not cover: generic code that RAPx verifies through a finite set of instances ([§8.6.1](#861-monomorphization)), loops that it unrolls only a bounded number of times ([§8.6.2](#862-loops)), and the specifications it trusts ([§8.6.3](#863-trusted-specifications)). Problems in individual checks are tracked as RAPx issues ([§8.6.4](#864-tracked-issues)).

## 8.6.1 Monomorphization

RAPx keeps the element type `T` of a generic function symbolic: its size and alignment are the symbols `sizeof_T` and `align_T`, so the function is proved once for all `T` instead of being instantiated. This is not enough when the function calls a trait method of another type parameter, as in `<[T]>::get_unchecked`:

```rust
pub const unsafe fn get_unchecked<I>(&self, index: I) -> &I::Output
where
    I: [const] SliceIndex<Self>,
{
    unsafe { &*index.get_unchecked(self) }
}
```

The implementation of `I` decides which code runs and whether the result is one element or a sub-slice. RAPx cannot resolve the call through a generic `I`, so it verifies the function once for each implementation of the bound, with `T` still symbolic, and labels the result `mono limit`.

How much such a result covers depends on the trait:

- **Closed trait.** All implementations are known. `SliceIndex<[T]>` can only be implemented inside `core`, and it has 25 implementations. If all of them are checked, the result is a complete case analysis for the current `core`. It must be rerun when `core` adds an implementation.
- **Open trait.** Any crate can add an implementation, so enumeration cannot be complete. RAPx also uses only implementations whose `Self` type has no type parameters. For `copy_within`, whose index is `R: RangeBounds<usize>`, this leaves only `RangeFull` ([10.1.3.23](./10.1-slice.md#101323-copy_within)). A proof for every `R` would treat the values returned by `start_bound()` and `end_bound()` as arbitrary, because `copy_within` checks them before any unsafe operation. RAPx does not support this yet.

`--trait-impl-limit` caps the number of instances and defaults to 1. The result is labeled `mono limit` whether one or all instances were checked; only the `(xN)` counts in the report show how many. Use a limit at least as large as the number of implementations, as [Chapter 10.1](./10.1-slice.md#1012-tool-integration) does with `--trait-impl-limit 64`. With such a limit, the result for a closed trait is a complete proof for the current `core`; open traits are left to future work.

## 8.6.2 Loops

RAPx does not use loop invariants. It unrolls each loop a bounded number of times (`--postfix-repeat`, chosen automatically by default; see [§8.4.1](./8.4-pipeline.md#841-path-extraction)) and collects at most `--path-limit` paths per search (default 256). Paths with more iterations are not checked, and paths cut by the limit are treated as proved; the result is then labeled `path limit`.

So `SOUND (with path limit)` means that no violation was found on the enumerated paths. It is not a proof for every number of iterations. Such a proof needs a loop invariant, which reduces the unbounded iterations to one induction step. Support for loop invariants is planned in future RAPx work.

## 8.6.3 Trusted Specifications

Every proof relies on specifications written by hand:

- preconditions of unsafe callees, given by `#[rapx::requires]` or by [`std-api-requires.json`](https://github.com/safer-rust/RAPx/blob/main/rapx/src/contract/assets/std-api-requires.json);
- contracts of trait methods in [`std-trait.json`](https://github.com/safer-rust/RAPx/blob/main/rapx/src/contract/assets/std-trait.json), with `requires` for callers and `ensures` for the result ([§8.3](./8.3-contracts.md));
- type invariants in [`std-type-invariants.json`](https://github.com/safer-rust/RAPx/blob/main/rapx/src/contract/assets/std-type-invariants.json), such as the slice invariant used in [§10.1.3](./10.1-slice.md#1013-function-by-function-verification).

RAPx assumes these specifications are correct when it verifies a caller. For example, the proof of `get_unchecked` uses the postcondition `SliceOffset(return, slice, self)` of `SliceIndex::get_unchecked`. Most of the 25 implementations are not yet verified against it: `--mode scan` on `slice::index` proves `SliceOffset` for only a few of them and reports `Unknown` for the rest. A `SOUND` result holds only if these specifications are correct. Checking the specifications themselves, such as the `SliceOffset` postcondition of every `SliceIndex` implementation, is future work.

## 8.6.4 Tracked Issues

Smaller problems in individual checks are reported as RAPx issues and fixed with a regression test. Each of them affects the soundness of RAPx's proofs: a check reported `Proved` for a program that violates the property. The table lists the issues found while reviewing [Chapter 10.1](./10.1-slice.md). An open issue is a known limitation of the current version.

| Issue | Check | Problem | Status |
|---|---|---|---|
| [#332](https://github.com/safer-rust/RAPx/issues/332) | `Align` | A pointer to a projection type such as `<I as SliceIndex<[T]>>::Output` was treated as aligned to 1. | Fixed in [#344](https://github.com/safer-rust/RAPx/pull/344) |
| [#333](https://github.com/safer-rust/RAPx/issues/333) | `InBound` | An index checked for a slice was accepted for a shorter view of the same slice. | Fixed in [#346](https://github.com/safer-rust/RAPx/pull/346) |
| [#334](https://github.com/safer-rust/RAPx/issues/334) | `Alias` | The escape check was skipped when the pointer came from a function call. | Fixed; regression test in [#348](https://github.com/safer-rust/RAPx/pull/348) |
| [#339](https://github.com/safer-rust/RAPx/issues/339) | `Allocated` | A slice pointer with the wrong length was accepted at a dereference. | Fixed in [#349](https://github.com/safer-rust/RAPx/pull/349) |
| [#351](https://github.com/safer-rust/RAPx/issues/351) | `InBound` | A dereference of a slice pointer checked only its first element. | Fixed in [#352](https://github.com/safer-rust/RAPx/pull/352) |
