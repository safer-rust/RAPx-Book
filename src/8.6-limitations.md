# Chapter 8.6. Limitations

A `SOUND` result means that every obligation RAPx checked was proved. This chapter describes what such a result does not cover: generic code that RAPx verifies through a finite set of instances ([§8.6.1](#861-monomorphization)), and loops that it unrolls only a bounded number of times ([§8.6.2](#862-loops)).

## 8.6.1 Monomorphization

RAPx keeps the element type `T` of a generic function symbolic. Its size and alignment are the symbols `sizeof_T` and `align_T`, so the function is proved once for all `T` instead of being instantiated. This works because the code of the function is the same for every `T`. Only sizes and alignments differ. It does not work for a type parameter whose trait methods the function calls, as in `<[T]>::get_unchecked`:

```rust
pub const unsafe fn get_unchecked<I>(&self, index: I) -> &I::Output
where
    I: [const] SliceIndex<Self>,
{
    unsafe { &*index.get_unchecked(self) }
}
```

Each implementation of `SliceIndex` has its own `get_unchecked` method and its own `Output` type. For `usize`, the method selects one element of type `T`. For `a..b`, it selects a sub-slice of type `[T]`. With a generic `I`, RAPx cannot tell which of these methods runs or what the result looks like. It therefore verifies the function once for each implementation of the bound, with `T` still symbolic, and labels the result `mono limit`.

Such a case analysis is complete only if the implementations of the trait are finite and all known. Rust decides this by where a trait may be implemented:

- **Implementations restricted to one crate.** A trait declared with an `impl(crate)` restriction can only be implemented in its own crate, so all of its implementations are known when that crate is compiled. `SliceIndex` is declared as [`pub impl(crate) const unsafe trait SliceIndex<T: ?Sized>`](https://github.com/rust-lang/rust/blob/65ce8611fed3142053320be6996ef00e9992671f/library/core/src/slice/index.rs#L124), and `[T]` has 25 implementations in `core`. If RAPx checks all of them, the result is a complete case analysis for the current `core`. It must be rerun when `core` adds an implementation.
- **Implementations allowed in any crate.** A trait without this restriction can be implemented in any crate that depends on it, so its implementations are not all known when `core` is verified, and no enumeration is complete. `RangeBounds` is declared as [`pub const trait RangeBounds<T: ?Sized>`](https://github.com/rust-lang/rust/blob/65ce8611fed3142053320be6996ef00e9992671f/library/core/src/ops/range.rs#L838). In addition, RAPx uses only implementations whose `Self` type has no type parameters. For `copy_within`, whose index type is `R: RangeBounds<usize>`, this leaves only `RangeFull` ([10.1.3.23](./10.1-slice.md#101323-copy_within)). A proof for every `R` would treat the values returned by `start_bound()` and `end_bound()` as arbitrary, because `copy_within` checks them before any unsafe operation. RAPx does not support this yet.

`--trait-impl-limit` caps the number of instances and defaults to 1. The result is labeled `mono limit` whether one or all instances were checked, and only the `(xN)` counts in the report show how many. With a limit at least as large as the number of implementations, as in [Chapter 10.1](./10.1-slice.md#1012-tool-integration), the result for a trait restricted with `impl(crate)` is a complete proof for the current crate. Traits that other crates can implement are left to future work.

## 8.6.2 Loops

RAPx does not use loop invariants. It unrolls each loop a bounded number of times (`--postfix-repeat`, chosen automatically by default; see [§8.4.1](./8.4-pipeline.md#841-path-extraction)) and collects at most `--path-limit` paths per search (default 256). Paths with more iterations are not checked. Paths cut by the limit are treated as proved, and the result is labeled `path limit`.

A `SOUND (with path limit)` result therefore means that no violation was found on the enumerated paths. It is not a proof for every number of iterations. Such a proof needs a loop invariant, which reduces the unbounded iterations to one induction step. Support for loop invariants is planned in future RAPx work.
