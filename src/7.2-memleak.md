# Chapter 7.2. Memory Leakage Detection

Rust's ownership model normally runs destructors when values leave scope. APIs such as `Box::into_raw` can transfer an owned allocation to a raw pointer, making the caller responsible for eventually freeing it.

The current `rCanary` detects some leaks across that ownership boundary by replaying MIR in RAPx's shared symbolic VM. It tracks allocation identity and whether a released allocation is freed, retained, or may escape. Its entry point is [`rapx/src/check/rcanary.rs`](https://github.com/safer-rust/RAPx/blob/main/rapx/src/check/rcanary.rs).

## Leak Pattern

An orphan allocation has been detached from Rust's automatic ownership system (for example, converted to a raw pointer with `Box::into_raw`) but is neither freed nor transferred to another owner.

```rust
fn main() {
    let buf = Box::new("buffer");
    let _ptr = Box::into_raw(buf); // ownership is released; nothing frees it
}
```

## Architecture

rCanary now uses the same symbolic VM as verification and SafeDrop. It does not run `HeapOwnershipAnalyzer`, encode ADT field layouts, or build the old rCanary-specific SMT-LIB2 flow constraints.

1. The checker selects local functions with a call that moves an ADT value and returns a raw pointer, reference, or tuple containing one. `Box::into_raw` is a typical example.
2. `PathAnalyzer` enumerates paths to function returns. The checker skips truncated paths and functions whose result or external storage could retain the pointer, avoiding a leak report when ownership might escape.
3. For each eligible path, `VmExecutor` runs MIR statements and calls. rCanary records the allocation released into the raw result and follows that allocation by VM provenance through subsequent operations.
4. At a supported return, it reports a candidate if the allocation is still live and has not been marked as possibly freed or escaped. The report points to the ownership-release call.

This is path-sensitive leak detection for supported ownership-release patterns. It does not claim to classify every owning type or every possible proxy type.

### Source Structure

| File | Purpose |
|------|---------|
| `rcanary.rs` | Entry point and warning emission for functions with detected leaks |
| `rcanary/vm.rs` | Candidate selection, path replay, allocation tracking, and leak detection |
| `rcanary/report.rs` | Source-location diagnostic formatting |

## Usage

### Prerequisites

Before using rCanary, install the Z3 solver (minimum version 4.10):

```shell
# macOS
brew install z3

# Ubuntu/Debian
apt-get install z3
```

### Running rCanary

Navigate to the root directory of a Cargo program and run:

```shell
cargo rapx check -m
```

> Note: Analysis requires the `nightly` toolchain with `rustc-dev`, `rust-src`, and `llvm-tools-preview` components installed.

### Output

When a leak is detected:

```
22:10:39|RAP|WARN|: Memory Leak detected in function main
warning: Memory Leak detected.
 --> src/main.rs:3:16
  |

4 | }
```

## Previous Implementation

The rCanary paper cited below describes the earlier implementation. It used an ADT type analysis to classify owning fields and proxy types. A separate flow analyzer then built ownership and drop constraints from MIR and sent them to Z3. That architecture is shown below:

![Previous rCanary type-analysis framework.](figure/rcanary.png)

That implementation used `HeapOwnershipAnalyzer`, `Encoder`, and `ranalyzer` modules, as well as diagnostic environment variables such as `ADTRES`, `Z3GOAL`, and `ICXSLICE`. The current rCanary is a later VM-based implementation: it tracks released allocations by provenance along explored paths and reports supported leaks from the resulting memory state. The paper remains the reference for the original method, but its type-analysis and flow-constraint pipeline does not describe the current code.
