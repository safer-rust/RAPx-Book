# Chapter 7.1. Dangling Pointer Detection

Rust uses ownership-based resource management (OBRM) and automatically deallocates unused resources without a garbage collector. This approach can potentially lead to premature memory deallocation, resulting in use-after-free or double-free errors. A significant portion of these bugs is related to the unwinding path, making them difficult to detect through testing or dynamic analysis. The [SafeDrop paper](https://dl.acm.org/doi/10.1145/3542948) describes the previous implementation; the current implementation is described below.

The implementation lives at [`rapx/src/check/safedrop/`](https://github.com/safer-rust/RAPx/blob/main/rapx/src/check/safedrop/).

## PoC

Below is a toy example demonstrating a Rust program with a use-after-free bug. The `Data` object is automatically dropped once the program exits the inner block scope of main. Accessing `ptr` after this point triggers a use-after-free error.

```rust
struct Data {
    value: Box<i32>,
}

impl Data {
    fn new(value: i32) -> Data {
        Data { value: Box::new(value) }
    }

    fn print_value(&self) {
        println!("Value: {}", self.value);
    }
}

fn main() {
    let ptr: *const Data;

    {
        let data = Data::new(42);
        ptr = &data as *const Data;
    } // data is automatically dropped here, leaving ptr dangling.

    unsafe {
        (*ptr).print_value(); // use-after-free.
    }
}
```

## Usage

To detect such bugs, navigate to the project directory and execute:

```shell
cargo rapx check -f
```

RAPx outputs a warning message in yellow if bugs are detected:

```shell
21:49|RAP-FRONT|WARN|: Use after free detected in function "main"
21:49|RAP-FRONT|WARN|: Location: src/main.rs:27:9: 27:20 (#0)
21:49|RAP-FRONT|WARN|: Location: src/main.rs:27:9: 27:34 (#0)
```

## Mechanism

The current SafeDrop implementation is based on the shared [symbolic VM](./6-vm.md). It tracks each allocation's provenance and lifetime on individual paths rather than relying on precomputed MOP alias summaries. This can distinguish allocations that a merged alias summary would treat alike, improving precision for those cases. The detection flow is:

1. `PathAnalyzer` enumerates paths through each eligible local function.
2. For each path, SafeDrop runs the MIR statements and terminators through `VmExecutor` with memory events enabled. Calls use the VM's call handling and may produce multiple symbolic states.
3. VM `MemoryEvent` records identify drops and uses of allocations. A second drop of an already dead allocation is a double free; a use after death is use-after-free.
4. At a return or cleanup exit, SafeDrop also checks whether a returned pointer or pointer argument still refers to a dead allocation. It reports a dangling pointer when it does.
5. The findings are collected by allocation identity and reported with source locations. Paths are checked independently, including cleanup paths.

The VM handles pointer provenance and memory state. SafeDrop adds the bug-specific event classification and reporting around that execution.

### Source Structure

The `safedrop/` module is organized as follows:

| File | Purpose |
|------|---------|
| `safedrop.rs` | Entry point and path enumeration |
| `safedrop/vm.rs` | VM replay, memory-event classification, and finding collection |
| `safedrop/bug_records.rs` | Bug records and source-location reports |

## Previous Implementation

The SafeDrop paper cited below describes the earlier implementation. It ran MOP alias analysis first, then used `SafeDropGraph`, `AliasGraph`, and points-to information to propagate drop state along paths and across calls.

The current SafeDrop is a later VM-based implementation. It follows allocation identity and lifetime along each explored path and classifies the VM's use and drop events. This can distinguish allocations that the earlier merged alias summaries treated alike. The paper remains the reference for the original method, but its implementation details do not describe the current code.
