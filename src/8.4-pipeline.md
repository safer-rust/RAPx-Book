# Chapter 8.4. The Verification Pipeline

This chapter walks through the verification pipeline using the [`linked_list_nonnull`](https://github.com/safer-rust/RAPx/blob/main/rapx/tests/verify_cases/linked_list_nonnull/src/lib.rs) case study — a doubly-linked list built with `NonNull<Node>` pointers:

```rust
#[rapx::invariant(Align(head.unwrap_some(), Node))]
#[rapx::invariant(Allocated(head.unwrap_some(), Node, 1))]
#[rapx::invariant(Typed(head.unwrap_some(), Node))]
#[rapx::invariant(Owning(head.unwrap_some()))]
#[rapx::invariant(Align(tail.unwrap_some(), Node))]
#[rapx::invariant(Allocated(tail.unwrap_some(), Node, 1))]
#[rapx::invariant(Typed(tail.unwrap_some(), Node))]
#[rapx::invariant(Owning(tail.unwrap_some()))]
struct LinkedList { head: Option<NonNull<Node>>, tail: Option<NonNull<Node>> }
```

For each target the pipeline runs: **path extraction → backward slicing → symbolic VM execution → property checking**. Property checkers use facts and rules from the VM state, invoking Z3 where needed. The sections below use `<LinkedList as Drop>::drop` as the running example — it has two unsafe callsites (`as_ref` for `Ptr2Ref`, `Box::from_raw` for `Allocated`/`Owning`/`Alias`) inside a `while let` loop, making it a compact but representative walkthrough.

## 8.4.1 Path Extraction

The first stage enumerates bounded paths from function entry to each unsafe callsite using `PathGraph`'s SCC decomposition (see [§5.1 Path Analysis](./5.1-path.md) for the algorithm). A path is a sequence of basic block IDs and can revisit blocks when a loop is unrolled.

The `drop` function contains a `while let` loop over the linked list nodes:

```rust
fn drop(&mut self) {
    let mut current = self.head;
    unsafe {
        while let Some(node) = current {
            current = node.as_ref().next;        // ← Ptr2Ref at as_ref
            drop(Box::from_raw(node.as_ptr())); // ← Allocated/Owning/Alias at from_raw
        }
    }
}
```

The `while let` body forms an SCC (bb2 → bb3 → bb4 → bb5 → bb6 → bb1 → bb2). Depending on the repeat budget, the path extractor unrolls this SCC, producing one path per loop iteration depth:

**Checkpoint `bb2 -> as_ref` (`Ptr2Ref`):**

```
path [0, 1, 2]                                  → 1 element, 1st iteration
path [0, 1, 2, 3, 4, 5, 6, 1, 2]               → 2 elements, 2nd iteration
path [0, 1, 2, 3, 4, 5, 6, 1, 2, 3, 4, 5, 6, 1, 2]  → 3 elements, 3rd iteration
```

**Checkpoint `bb4 -> from_raw` (`Allocated`/`Owning`/`Alias`):**

```
path [0, 1, 2, 3, 4]                            → 1 element
path [0, 1, 2, 3, 4, 5, 6, 1, 2, 3, 4]         → 2 elements
path [0, 1, 2, 3, 4, 5, 6, 1, 2, 3, 4, 5, 6, 1, 2, 3, 4]  → 3 elements
```

Each path records exactly one visit to the target callsite after the prescribed number of loop iterations. The sections below use the **shortest from_raw path** as the running example:

```
path [0, 1, 2, 3, 4]   →   Allocated/Typed/Owning | Proved, Alias | Proved
```

The extractor builds a `PathTree` for the function and slices prefixes to each checkpoint. The default path-count limit per search is 512; `--path-limit=N` overrides it. Path enumeration also has traversal-depth limits. When a limit truncates the tree, unenumerated paths are currently treated as proved, so a passing report may say `SOUND (with path limit)`. By default, `auto` mode chooses a repeat budget before path extraction. With `--postfix-repeat=N`, verification runs every repeat depth from 0 through N.

## 8.4.2 Backward Slicing

Take the path `[0, 1, 2, 3, 4]` — a single-element list: `self.head` is `Some`, the `while let` enters once, `as_ref` at bb2 exposes the node, and `Box::from_raw` at bb4 frees it. The relevant MIR blocks:

```
bb0:  {
    _2 = move (_1.0: Option<NonNull<Node<T>>>)   // current = self.head
}
bb1:  {
    _3 = discriminant(_2)
    switchInt(move _3) → [0: bb7, 1: bb2]         // None → exit, Some → loop
}
bb2:  {
    _4 = copy ((_2 as Some).0)                    // extract NonNull from Option
    _6 = &mut _4
    _5 = NonNull::<Node<T>>::as_ref(move _6)      // ← CHECKPOINT: Ptr2Ref
}
bb3:  {
    _7 = &(*_5).next
    _2 = move _7                                  // current = node.next
}
bb4:  {
    _8 = NonNull::<Node<T>>::as_ptr(copy _4)
    _9 = Box::<Node<T>>::from_raw(move _8)        // ← CHECKPOINT
}
bb5:  {
    drop(_9)                                      // free the Box
}
bb6:  {
    goto → bb1                                    // loop back
}
bb7:  {
    return
}
```

The `BackwardSlicer` extracts only the MIR statements that contribute to the target place's value — everything else is dropped.

Walk backward from `_9 = Box::from_raw(move _8)`:

| Step | Collected | Provides |
|------|-----------|----------|
| bb4 | `_8 = as_ptr(copy _4)` | `_8` → `_4` |
| bb2 | `_4 = ((_2 as Some).0)` | `_4` → `_2` |
| bb0 | `_2 = (_1.0)` | `_2` → `_1.0` (self.head) |

The collected chain is `_9 → _8 → _4 → _2 → _1.0` (where `_1.0` is the `head` field of `LinkedList`). The slicer recognises standard-library calls by their effects: `NonNull::as_ptr` → returns a raw pointer to the same allocation; `((_2 as Some).0)` → projection from `Option` to inner `NonNull`.

No `ContractFact` items are injected — `drop` has no `#[rapx::requires]` of its own.

## 8.4.3 Symbolic VM Execution

The `SymbolicVm` ([`vm/mod.rs`](https://github.com/safer-rust/RAPx/blob/main/rapx/src/verify/vm/mod.rs)) is a semantic MIR executor that replaces the earlier pattern-matching forward verifier. Instead of deriving ad-hoc facts from MIR patterns, it executes the retained MIR items from the backward slicer and directly builds symbolic state (`VmState`) with Z3 terms for every value.

### 8.4.3.1 Building symbolic state before the checkpoint

The VM executes retained MIR items in forward path order. Each MIR statement and terminator is translated into a transfer function that updates `VmState`:

| BB | MIR statement | VM effect |
|----|--------------|-----------|
| bb0 | `_2 = move (_1.0)` | Reads `self.head` (an `Option<NonNull<Node<T>>>`) into local `_2`; provenance from the caller is inherited |
| bb1 | `switchInt(discriminant(_2)) → [1: bb2]` | Path condition: `_2` is `Some` (enforced by branch taken) |
| bb2 | `_4 = copy ((_2 as Some).0)` | Projects the `NonNull<Node<T>>` pointer out of `_2`; `_4` points to the same allocation as `self.head` |
| bb2 | `_5 = as_ref(&mut _4)` | **checkpoint**: `Ptr2Ref` on `_4` — verifies `Init`/`Align`/`Alias` |
| bb3 | `_2 = move &(*_5).next` | Reads the `next` field of the dereferenced node; updates `current` for the next iteration (not needed for the `from_raw` chain) |
| bb4 | `_8 = as_ptr(copy _4)` | Raw pointer to the same allocation |
| bb4 | `_9 = Box::from_raw(move _8)` | **checkpoint**: `_8` resolves to origin `_1.0` (self.head) |

At execution time, the VM tracks:

- **`current_frame.local_alloc`**: each MIR local's stack allocation in the current frame;
- **`units`**: memory units holding allocation shape, typed values, byte-level initialization state, and facts;
- **`constraints`**: solver assertions and cached terms, including conditions from taken branches;
- **`caller_frames`** and **`inline`**: saved frames and state for inlined calls.

At the `from_raw` checkpoint, the verifier resolves the value chain `_9 → _8 → _4 → _2 → _1.0` through the VM's provenance tracking. The origin `_1.0` (`self.head`) is a `NonNull<Node<T>>` pointer stored in the struct — its provenance was tracked from the struct invariant that guarantees `Allocated(head.unwrap_some(), Node, 1)`.

### 8.4.3.2 Hazard tracking (Alias)

`Box::from_raw` declares an `Alias(p, ret)` hazard. The alias checker resolves the pointer's allocation and origin, considers live reference views and subsequent raw-pointer accesses, and checks whether a matching caller contract discharges the hazard. It does not simply require that no other pointer or field names the allocation. See [§8.5.3](./8.5-verification-approach.md#853-the-alias-hazard) for the current check.

## 8.4.4 Property Checking

The `PropertyChecker` ([`property_checker`](https://github.com/safer-rust/RAPx/blob/main/rapx/src/verify/property_checker/mod.rs)) dispatches each safety property to a dedicated checker. Those checkers use the VM's facts and allocation model, with SMT queries where needed:

- **Value-definition chain.** MIR assignments create symbolic Z3 terms for each local. `_8` is defined as the raw pointer from `_4`, which projects from `_2`, which originates from `self.head`. The Z3 model follows this value chain — no separate equality assertion needed.
- **Allocation model.** Each allocation records its base address, element size (from `sizeof(T)`), and element count. The VM asserts that the address range is within the allocation bounds.
- **Initialization tracking.** `Allocated` describes an allocation and its extent; initialization is tracked separately through allocation content and `Init` facts.
- **Path conditions.** The `switchInt` at bb1 constrains the solver: `_2` is `Some`.

For an SMT-backed obligation, the checker asserts the path constraints and negates the goal: `Unsat` proves the goal under those constraints. Other obligations can be proved or rejected by direct rules, and unsupported or incomplete cases return `Unknown`. The detailed rules are in [§8.5](./8.5-verification-approach.md).

For `Box::from_raw` on `_8`, five obligations are checked:

### Align

```
constraints ∧ ¬(_8 % align_of::<Node<T>>() = 0)
```

The struct invariant `Align(head.unwrap_some(), Node)` supplies an alignment fact that can follow the pointer value through `_1.0 → _2 → _4 → _8`. The checker may discharge the property from that fact or use a modulo query for the required alignment.

### Allocated

`Allocated` checks that `_8` resolves to a live allocation with enough space for the requested object.

- **Is an allocation tracked?** The struct invariant `Allocated(head.unwrap_some(), Node, 1)` provides a fact about the pointed-to allocation.
- **Is its extent sufficient?** The requested object must fit within the tracked allocation.

The checker can use the recorded allocation facts and, where necessary, a size or bounds query.

### Typed

`Typed(p, T)` concerns the allocation's element type or a compatible field view. The checker compares the resolved pointer's provenance and type information with the required `Node<T>`; this is primarily a rule-based check, not a negated SMT goal.

### Owning

`Owning(p)` checks ownership of the resolved allocation. The checker uses ownership facts and examines live owners that would also drop the same allocation; it does not infer sole ownership merely from the `&mut self` receiver. The `Owning(head.unwrap_some())` invariant supplies the relevant struct-field fact.

### Alias

`Alias` is handled by the VM alias checker described in §8.4.3.2 and [§8.5.3](./8.5-verification-approach.md#853-the-alias-hazard). Its result is rule-based (`Proved`, `Failed`, or `Unknown`), rather than a single query for whether another pointer exists.

## 8.4.5 Auto-Repeat Planner

For the `bb4 -> from_raw` checkpoint, `Box::from_raw` requires `Allocated`, `Owning`, `Alias`, `Align`, and `Typed`. The auto-repeat planner looks for safety sinks that depend on loop-carried state and for numeric obligations that may fail only after several iterations. It uses those hints to choose a bounded repeat depth; it does not establish that invariants hold at deeper iterations. The shortest path (depth 0) contains a single loop iteration:

```
depth 0:  path [0, 1, 2, 3, 4]               — 1  body iteration
depth 1:  path [0, 1, 2, 3, 4, 5, 6, 1, 2, 3, 4]    — 2  body iterations
depth 2:  path [0, 1, 2, 3, 4, 5, 6, 1, 2, 3, 4, 5, 6, 1, 2, 3, 4]  — 3  body iterations
```

In the report excerpt above, the checked paths are proved at the selected depths. Repeated rounds can check the same shorter path more than once, producing `Proved (x3)`. This observation applies to those enumerated paths, not to every possible iteration of the loop.

The repeat planner only decides how many loop repetitions should be explored. The backward slicer, symbolic VM, and property checkers then run on the extracted paths.
